## First, a GitHub Account + First-Time Login

> To push, you first need "a home in the cloud" + "proof that you are you." Beginners often get stuck here — they can type the git commands but hit an authentication wall on the first push. This chapter smooths it out.

### 1. Create Your Own GitHub Account

- Why you need it: GitHub = the cloud where your repo lives; without an account there's nowhere to push.
- Steps: register at [github.com](https://github.com) → choose the **Free plan** (unlimited public repos for personal learning, $0 is plenty).
- Pick a recognizable, somewhat professional username (it becomes your portfolio URL, e.g. `github.com/your-username`).

### 2. The First Push Hits an "Auth Wall" — Get Past It with `gh auth login`

- ⚠️ **Key pitfall**: GitHub has long **disallowed pushing with a password**. The first push prompts for authentication, and not understanding it is where people stall.
- For beginners, **the least painful path = GitHub CLI's `gh auth login`** (interactive login — just follow the prompts; no manually wrangling tokens / SSH keys).

**Hands-on:**

1. First install GitHub CLI (this is your first encounter with **Homebrew** — macOS's package manager, a general skill worth learning):
   ```sh
   # If Homebrew isn't installed yet, install it from brew.sh using the official one-line command
   brew install gh
   ```
2. Interactive login:
   ```sh
   gh auth login
   ```
   Follow the prompts: `GitHub.com` → `HTTPS` → log in via browser → paste the one-time code shown → done.
3. After this, `git push` won't ask for a password / token again — authenticated once and for all.

> Mental model: `gh auth login` = "check in with GitHub once on this computer." Once checked in, this computer is trusted and pushing flows freely.

## 🔴 Core Rule: What Goes Into git, What Doesn't

> Teach this as the **core rule** of the git lesson, not a footnote — it's a general notion of "what belongs in version control," highly educational for researchers.

| Goes into git ✅ | Stays out of git ❌ |
|------------------|---------------------|
| Code (`.py` / `.R` / `.ipynb`) | **De-identified cohort data (CSV / any data file)** |
| Documentation (CLAUDE.md / PROGRESS / TODO / README) | Large outputs (model weights / images / intermediate files) |
| Config files | Anything containing any ID |

- **The rule in one line**: **git holds "how you did it" (code + docs), not "the data itself."** Data stays local / in institutional storage, managed separately.
- Why:
  1. Even de-identified, putting a cohort in the cloud still carries compliance / IRB concerns.
  2. Data files are large and change frequently — git is a poor fit.
  3. Keeping research data out of git by default is a widely accepted best practice.
- Operationally, use `.gitignore` to exclude data (expanded in the next chapter).

## `.gitignore` — Turn the Policy Above Into a File

> Policy (what stays out of git) → operation (how to actually block it). A `.gitignore` is simply a list of "git, please ignore these," placed in the project root.

### A Starter Template for Clinical Researchers

Copy this as your base; each line blocks one category:

```gitignore
# --- Data never goes into git (the core rule) ---
*.csv
*.xlsx
*.sas7bdat
*.dta
data/
cohort/

# --- System / editor noise ---
.DS_Store
.vscode/

# --- Python ---
__pycache__/
*.pyc
.ipynb_checkpoints/
.env
```

- `*.csv` / `*.sas7bdat` etc. = block all data files by extension (wherever they sit).
- `data/` / `cohort/` = exclude entire folders (keep your data in these two folders and you're covered for good).
- `.DS_Store` / `__pycache__/` = noise auto-generated by the system / programs; shouldn't be in version control.
- `.env` = the file holding passwords / keys — **must never go to the cloud**.

### ⚠️ The Most Common Trap: "I Added It to `.gitignore` — Why Is It Still There?"

- **Key concept**: `.gitignore` **only blocks files not yet tracked by git**. A file that has **already been committed** can't be un-tracked by adding it to `.gitignore` afterward.
- To remove an already-tracked file: run `git rm --cached <file>` first (removes it from git but keeps the local copy), then commit.
- **The least-effort mindset**: **create the `.gitignore` first, then `git add`** — get the order right and you'll never get caught. The first thing in a new project is to set up `.gitignore`.

## Data Compliance (PHI) — Lesson 1 Gave the Bottom Line; Here We Expand

- Pushing to GitHub = public / semi-public cloud, so "data stays out of git" is simultaneously a version-control best practice and a privacy safeguard.
- Key points:
  - **De-identify before it goes up**: any data going to the cloud (git / cloud drives / AI chat) should be de-identified first.
  - **Mind photo metadata**: the EXIF of medical photos may contain identifiable info such as capture date / device / location.
  - **Compliance environments differ across AI services**: different AI subscription plans have different data-handling terms; a consumer-grade plan is **not** equivalent to a BAA (HIPAA Business Associate Agreement) environment. Before any PHI is involved, confirm your tool is compatible with your institution's rules.
  - Defer to your own institution's IRB / data-governance rules as the final authority.
